# Security — Client-Side Persistence Threat Model

Scope: Gallop is a purely client-side simulation. There is no backend, no
account system, and no network sync — `src/` contains zero `fetch(`,
`XMLHttpRequest`, `sendBeacon`, or `WebSocket` call sites (a test even asserts
the person-manifest source stays `fetch`-free). The analytics "tracker" queues
events to localStorage only; nothing is transmitted. All persistence happens
in the browser. This document records where state lives, what the data
contains, and which storage-related findings are accepted risks.

## Data classification

Persisted data is simulation state plus user-entered display names
(`playerProfile.stableName`, `owner.biography.displayName`), UI preferences,
bookmarks/tags, a local-only analytics queue, and any dataset the user
imports via CSV. There are no credentials, tokens, emails, or other PII. The
consequence of exposure is bounded: a same-origin script could read or tamper
with one user's save on that user's own machine.

## Threat model

The relevant attacker is a same-origin script (XSS or a compromised
dependency). Storing state unencrypted does not change that attacker's power:

- Web storage (localStorage, sessionStorage, IndexedDB) is equally readable
  by any same-origin script; encrypting only the localStorage fallback while
  IndexedDB holds the same plaintext would be cosmetic.
- Any encryption key would have to be shipped to or generated by the same
  client, so a script that can read the store can also invoke the decrypt
  path. Client-side encryption here is obfuscation, not a security boundary.
- Obfuscation may still deter casual save-editing via devtools, and plaintext
  deliberately keeps saves inspectable/back-up-able — a design property, not
  an oversight.

The real controls for injected-script risk are XSS prevention and CSP /
dependency hygiene, which are tracked separately from this document.

## Accepted-risk register

| Finding | Location | Status | Rationale | Re-evaluate if |
| --- | --- | --- | --- | --- |
| Unencrypted game state in localStorage | `src/platform/game/store/storage.ts:114` | **Accepted** (2026-11-10) | Standard practice for client-side sims; impact negligible (game data only, same plaintext in IndexedDB regardless); plaintext is the intended design so saves stay inspectable. | The app adds accounts, server sync, multiplayer, payments, or any real secret / cross-user data in the persisted state. |

## Guidance for future format changes

If the stored format ever changes (encoding, compression, export format):

1. **Cover all state sinks** — IDB buckets, the `saveSlots` store,
   `gallop_game_state_fallback`, and `gallop_save_*` slot keys. Changing only
   `storage.ts:114` leaves identical plaintext in IndexedDB.
2. **Tests first.** Any implementation of a format change must land its test
   updates *before* the implementation: failing encode/decode round-trip
   tests, updated seed helpers, and dual-read fixtures (see below).
3. **Backward compatibility is a test-harness concern, not a user-save
   concern.** Existing saves have no migration guarantee —
   `onRehydrateStorage` already wipes saves on `storeVersion` mismatch
   (`src/platform/game/store/index.ts:362`), so a hard cutover is acceptable.
   The real constraint is the test harness: jsdom-based unit tests exercise
   the fallback (jsdom has no IndexedDB), and five Playwright specs plus
   several unit tests seed **plaintext** into `gallop_game_state_fallback`
   (`weather.spec.ts`, `visual.spec.ts`, `analytics-awards-smoke.spec.ts`,
   `horse-compare-layout.spec.ts`, `npc-stable-roster-layout.spec.ts`,
   `storageAdapter.test.ts`, `phantomSave.test.ts`). Either keep a dual-read
   path that accepts legacy plaintext, or update every seed site to emit the
   new format via a shared encode helper. Both are valid; pick deliberately.
